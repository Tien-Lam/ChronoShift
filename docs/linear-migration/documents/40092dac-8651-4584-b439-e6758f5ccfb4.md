## Selected foundation and rationale

Adopt local shadcn/ui React Aria component recipes, backed by ChronoShift's existing React Aria fields/menu/date interaction stack. This remains the selected project approach. Record upstream source/version/licence, owned local adaptations, variants and upgrade policy. Deliver actual shared components and rendered state evidence.

This is a compatibility decision for ChronoShift, not a universal rule for future projects. The [default shadcn Button docs](https://ui.shadcn.com/docs/components/base/button), inspected on 7 October 2026, route to Base UI and provide React Aria and Radix alternatives. Future projects evaluate current upstream defaults and their own constraints using the shared playbook.

Map component geometry, typography, palette and motion to the [approved ChronoShift design spec](https://github.com/Tien-Lam/time-to-local/blob/main/docs/linear-migration/documents/e0a57819-2bcd-460c-91ea-207585eb6b1d.md). Keep the compact clock/name/Appearance header, workspace immediately below, no hero/title/intro, and privacy footer. Preserve warm Light/forest Dark/live System, local Geist, editor/result hierarchy and purposeful date/time/source/reference labels.

Existing approved motion/lifecycle corrections remain authoritative: readable semantic foreground/surface pairs switch atomically, transient decoration is bounded, controls and Copy targets stay stationary, disclosure close geometry commits immediately, reduced motion and live preferences remain supported.

## Project constraints and adoption boundaries

ChronoShift is local/offline. Preserve input/reference-date privacy, source/target independence, explicit ambiguity, range/precision/copy semantics, clipboard/import/focus ownership, resize/draft state, reset and user-explicit updates. Keep runtime assets/fonts under the Pages base path and no runtime CDN.

Build narrow owned ActionButton variants and applicable field/disclosure/menu shells on the selected recipes. Reuse tested searchable/date behavior during bounded migration. Keep conversion, clipboard/update operations and domain state outside the visual wrappers. Do not duplicate activation or retire touch handling before matching tests justify it.

If chosen recipes need Tailwind or other build tooling, document integration and emitted/offline assets. Record component exceptions and reasons. A new dependency, screenshot or generic wrapper alone does not satisfy adoption.

Use a development-only local state gallery and existing Playwright/axe tools; Storybook is optional if justified. Preserve all meaningful existing exact tests and add missing appearance/geometry/state/content checks. Pin visual baseline environments, review intentional changes and preserve original-failure controls.

## Current defect and immediate correction

User: “paste button when hovering over on desktop is misaligned (the highlight).”

At main 98c411f021410d751d5b40c4ff50fe5c650eade3, web/src/style.css defines .text-button padding 10px 12px, then overrides .input-tools .text-button to padding: 8px 12px 8px 0. Hosted IAB measurement confirms Paste: 44px height, approximately 44.10px width, left inset 0px/right inset 12px, centred text alignment and 8px radius. The content box therefore places the label about 6px left of the button's horizontal centre. Hover fills the button surface; this asymmetric geometry explains the off-centre appearance. It is source and resting-geometry evidence, not a full pointer-hover replay of the user's desktop session.

Remove the one-sided padding override and give Paste/Clear the shared quiet-action geometry. Use inline-flex, align-items:center, justify-content:center, gap for icons, padding-inline:12px and min-block-size:44px. Keep toolbar spacing/alignment on the parent via gap/padding; do not align text with its ancestor by trimming only one side of the interactive surface. Preserve clipboard rejection, editing/focus ownership and the delivered touch-feedback behavior.

Capture actual hover/rest/focus/press in both palettes, with and without Clear. An independent label-centre versus surface-centre expectation (approximately 1 CSS px tolerance for plain text, logical-direction-aware) should fail on the old defect and pass the correction. Do not use a test that only checks the new CSS declaration.

Local observed evidence: .work/design-system-research/paste-geometry.json. Exact original browser, zoom and viewport history are unknown.

## Project verification and delivery

Use actual shared controls and representative page compositions in rest/hover/focus/press/disabled and applicable pending/success/error states. Cover text/icons, adjacent actions, fields/help/errors, example/disclosure/zone/theme/calendar menus, results and compact header/footer.

Use Light/Dark/live System, 280/390px and representative desktop, normal/reduced motion, long/precision results, zoom and forced colours. Keep static visual/geometry evidence separate from native pointer/touch, interruption and focus evidence. Do not claim original handset history from browser emulation.

Run appropriate repository checks and lifecycle/PWA gates. Substantial implementation uses the repository's two clean independent reviewers, including the read-only code-review skill. Preserve full source/timing/original-attempt/review evidence in ignored ticket folders; concise matching acceptance on tickets/PR. Publishing follows the serialized main-only workflow when authorized.

Existing completed design/tap/semantics acceptance is preserved; each new migration/report needs matching evidence. This document update changes planning/docs and does not claim component migration or report closure.
