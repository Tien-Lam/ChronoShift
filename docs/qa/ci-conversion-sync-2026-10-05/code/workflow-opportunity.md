## Existing topology is already bounded

- Web runs for relevant PRs to main, not for every branch push. Main Pages first tries the trusted same-repository successful PR artifact, enforcing every required step, full head/release/main tree identity, archive digest and safe extraction. Missing/expired/unverifiable artifacts fall back to the complete Web gate. Manual publication also deliberately takes the full gate; retain that rollback/verification behavior.
- Both workflows already ignore Markdown, design/QA/experiment folders and the specifically listed planning evidence JSON. Docs-only PRs and main pushes therefore normally avoid both expensive gates and publication. The corpus audit JSON remains checked, and runtime/build/workflow files remain eligible. Do not broaden ignores to production assets, build inputs or tests simply to improve a number.
- PR Web concurrency cancels superseded work for the same PR; distinct PRs intentionally do not cancel each other. The entire Pages lifecycle is serialized and active deployment is not canceled. GitHub's default single pending slot already drops superseded pending publications; do not add `queue: max` or cancel active Pages work. [GitHub concurrency reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency).
- Read-only branch protection returned “Branch not protected,” and applicable main rules returned an empty list. Thus no skipped-required-check deadlock was observed in current settings. Adding required checks later needs deliberate handling of path-skipped runs. [GitHub path-filter behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).

## Ranked opportunities

1. **Group related GitHub Actions dependency updates before their full gate.** Dependabot currently allows five separate weekly GitHub Actions PRs and defines no groups. Current open PRs 17–21 are all separate Action updates; Web runs for PRs 18, 19 and 20 started within 14 seconds at 07:11:46–07:12:00, all successful. Their changed files are the Pages/Web workflows. One deliberately reviewed compatible batch can receive one complete PR gate and one final publication instead of several independent full browser gates and successive workflow-only deployments. Major-version changes still need individual compatibility analysis within the batch; no claim that the existing five upgrades are safe together. Dependabot supports per-ecosystem grouped version PRs through `groups` and `patterns`. This is a run-count opportunity with direct observed demand, not a claim of measured monthly savings. [Dependabot groups reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#groups).

2. **Finish local reviews/evidence before the final hosted PR gate; batch evidence commits.** A Markdown-only commit on an already-open runtime PR can still trigger Web because GitHub evaluates the PR's cumulative three-dot changed-file list, which retains the runtime change. It also changes the full tree required for artifact reuse. Save both original reviewer reports together before the final exact-head run, then preserve that run's result in durable PR text/comments rather than issuing another evidence commit solely to annotate it. Separately committed docs-only follow-ups after the runtime merge use the existing ignores. This preserves required review provenance and exact-tree trust while avoiding gratuitous reruns; it does not justify reusing a mismatching tree. PR 38 itself had one listed Web run, so this is a proven trigger semantic, not an allegation of repeated runs for that PR. [GitHub diff comparisons](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#git-diff-comparisons).

3. **Consider verification-only main changes separately from actual deployment eligibility.** Today e2e/unit-test/CI-metrics-only merges still enter Pages, create a new release marker/cache version and retain a rollback artifact although runtime inputs may be unchanged. A carefully bounded runtime/build/deployment-input classifier could keep full PR verification but omit a redundant publication for such main changes. Unknown/deployment/build/dependency changes must retain the full current path; actual runtime deployments must retain complete gates and exact trusted reuse. This needs explicit ownership for direct-main changes and review of the deployment-input closure (web/public, worker template, Vite/CSP/offline/notices scripts, dependencies/lock and deployment workflows). It is a separate topology change, not an immediate safe path-ignore addition. Current evidence does not quantify how many monthly publications would be avoided.

4. **Small repeated work inside each full gate:** `bun run build` runs TypeScript checking and notices generation twice, once for root and once for `/ChronoShift/`. Both root/subpath bundles, generated workers and browser checks remain necessary; their base paths differ. Only the unchanged-source typecheck/unchanged-dependency notice preparation is logically reusable within one successful job. A dedicated second-base build stage could retain Vite/offline generation and all assertions while avoiding that duplicate preparation. This is likely a small saving and needs ordinary gate verification; no timing or rounded-minute benefit was measured here.

Draft-PR suppression is a conditional additional run-count idea, not a present high-priority saving: all six currently open PRs are non-draft. If adopted, a `ready_for_review` trigger and trustworthy completed final gates are mandatory; merely skipping draft jobs would make readiness incomplete. Extending the one-day PR artifact retention might reduce future expiry fallbacks but increases storage and is not supported by observed expiry frequency, so it is not recommended from this audit.

No 20% acceptance or monthly-free-usage closure follows from these opportunities. Grouping/batching can reduce total runs while leaving every deployed runtime fully verified; their actual monthly effect needs a bounded inventory of avoided runs and artifacts.
