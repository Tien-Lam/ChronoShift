## Finding and distinction

**A public lower-level route can bypass the hidden React collection tree, but RAC ComboBox has no public prebuilt-collection switch.** This is source-derived feasibility, not a working prototype or adoption verdict. The relevant installed versions are React Aria Components1.21.1, react-aria3.52.1 and react-stately3.50.0, matching bun.lock. These lower packages are locked transitive dependencies rather than direct entries in the application's package.json; this assessment does not alter dependency declarations or claim that such imports would remain available under a different installer/layout.

The current candidate retains RAC ComboBox. `react-aria-components/dist/private/ComboBox.js:56–89` builds a `CollectionBuilder` from its children on every initial mount regardless of whether the popup is open. `ComboBoxInner:107–115` passes that completed collection to `useComboBoxState`, overriding any collection that might be spread from props. Public RAC ComboBoxProps do not declare a collection override. `react-aria/dist/private/collections/CollectionBuilder.js` renders a hidden copy, creates its synthetic collection Document and renders a portal into that Document on the client; SSR instead constructs collection nodes during shallow rendering. This is a synthetic document/React tree, not evidence that hundreds of visible option elements exist in the browser's closed-popup DOM. `Popover.js:60–74` intentionally retains children in that hidden tree while closed. `ListBox.js:72–90` explicitly describes the hidden building copy and the visible state-driven copy.

The public Virtualizer changes the latter's CollectionRoot rendering to visible/reusable views and persists focused keys. It does not eliminate the former. Thus a lower-level data-backed collection targets different material work: hidden item React/shallow portal/document construction for **both** mounted source and target pickers, even before first opening. It still constructs the full logical data collection; it does not remove filtering, state effects, option hooks for rendered rows, parser/worker work or animation.

## Actual public override and caching boundary

`react-stately/useComboBoxState` exports `ComboBoxStateOptions`, which extends `CollectionStateBase`; the latter publicly declares `collection?: C` as a preconstructed collection. Its `useComboBoxState.js:73–96` forwards that property to `useListState`. The latter calls `useCollection`, whose implementation immediately returns `props.collection` before `builder.build`. A CollectionBuilder object is still allocated per hook via useMemo, but no JSX node traversal/build occurs on this override path.

Public import paths are `react-stately/useComboBoxState`, `react-aria/useComboBox`, `react-aria/useListBox` (which exports both useListBox and useOption), `react-aria/useButton`, `react-aria/usePopover`, and `react-aria/Overlay`. The react-stately root publicly exports `Collection` and `Node` types, `Item`, `useCollection` and `useComboBoxState`. **ListCollection is not a public root export or implemented public ListCollection subpath in this locked version.** Its private source is useful evidence, but importing it through `/private/` would violate the public-only premise. A feasible public-only implementation would provide the structural Collection/Node interfaces itself. Alternatively public useCollection+Item and a custom collection factory can build JavaScript nodes without RAC's synthetic DOM, but still traverses Item JSX and is a less direct isolation of collection construction.

RAC's public Collection supports dependencies/cache invalidation, and its installed useCachedChildren already uses a WeakMap keyed by stable object identity; production callback changes alone do not create a new WeakMap. Those controls do not skip initial hidden node mounting/document construction. Merely hoisting callbacks, adding memo or reusing its JSX children is the already-rejected memoization direction, not this collection override.

A module-level complete collection or an eagerly initialized stable instance can hold all unchanged option data from first render. Selection/focus/input state must remain per picker; a shared data collection must not store mutable selection or focus. Module-level immutable data also must not capture one request's generated IDs, element refs, React contexts or state callbacks. No key/label/text/alias ordering can change to simplify construction.

## Collection and filtering requirements

The publicly exported Collection interface requires iteration, size, getKeys, getItem, at, getKeyBefore/After and getFirst/LastKey; getChildren/getTextValue/filter are optional. Every item Node needs the original ID as key, complete option value, `type: item`, `level`, child metadata, rendered/text fields and index. Metadata must cover every item, not only mounted rows. Correct prev/next/index/size semantics are essential to interior navigation and ARIA positions. Plain label/description data can be rendered only when the visible option mounts; no hidden JSX tree is intrinsically required by the state hook.

The installed useComboBoxState maintains its original full collection, a filtered collection, manual show-all state and a last collection for closing. Its built-in defaultFilter path runs only when `props.items` is absent; supplying controlled items would silently disable that filtering and alter manual-open behavior. Preserve `inputValue=value`, controlled `value=known ID or null`, existing independent commit deduplication/current ref, allowsCustomValue, allowsEmptyCollection, validationBehavior=aria and the existing normalized alias search using `node.textValue=option.id`. Keep `props.items` absent so built-in filter/manual-open semantics remain aligned with today's defaultItems path.

The current state hook's filterCollection constructs its own private ListCollection internally, which is permissible library-owned behavior. It clones matching item nodes and rewrites indexes/neighbor links for the filtered collection. That means full collection indexes and filtered indexes must remain separate and no custom cache may accidentally mutate shared original nodes. This route does not remove filtering's allocation/iteration; caching query results or replacing the state filter would be a separate, riskier experiment. Stable defaultFilter identity could avoid unrelated recomputation, but is not the material hidden-tree bypass and should not be conflated with it.

## Accessibility, focus and overlay ownership

`useComboBox` owns input/trigger references, list ID, aria-controls, aria-activedescendant, menu trigger, Apple announcements, input change/focus/blur, Enter/Tab commit, Escape revert and arrow opening/navigation. Pass its listBoxProps into useListBox, with **shouldFocusOnHover=false** overriding the hook's default true so pointer hover cannot change the value subsequently committed by Tab. Hook-returned inputProps must be applied to the real controlled input with merged diagnostic handlers; do not overwrite onChange/onFocus/onBlur/key handlers. Button props go through useButton, including pointer-type differences, excluded tab order and focus prevention. Separate useTextField on the same input would duplicate behavior already supplied by useComboBox and is unnecessary.

`useListBox` owns the same state/ref/ID mapping; `useOption` returns optionProps, labelProps and descriptionProps, plus focus/selection state. These must be attached to the actual elements, with the existing data-value and exact visible label/description content. Preserve generated IDs and their relationships through hook ownership rather than substituting an arbitrary option ID. The existing selected/focused/hovered/focus-visible CSS data attributes must be supplied from returned states/hover/focus hooks. No-match retains the current empty placeholder semantics and zero actual data-value choices. Manual focus and pointer should not compete with native input ownership.

A **nonvirtualized lower-level list** can preserve natural row wrapping by rendering all `state.collection` options only while its popup is mounted. That alone can isolate hidden-tree removal while leaving open row mounting comparable to baseline; it does not need estimated/fixed heights or a custom scroll engine. This would be a new standalone bounded candidate, not an amendment to the frozen Virtualizer candidate.

If combining the prebuilt collection with open-row virtualization later, public useVirtualizerState and ListLayout are exported from react-stately/useVirtualizerState, but the lower-level react-aria ScrollView/VirtualizerItem/useVirtualizerItem components inspected here are only private exports; their existence in private types is not a public integration contract. Reimplementing scroll observation/measurement/pointer shielding merely to avoid those private imports is a substantial independent lifecycle change.

There is a narrower **public RAC bridge to investigate**, not a proven drop-in: public ListStateContext lets RAC ListBox render a supplied state without CollectionBuilder; public Virtualizer/ListLayout can wrap it, and complete public Node.render functions could render custom useOption-backed rows via the public ListStateContext provided inside ListBox. Its current renderer invokes node.render and preserves focused keys. One would need to prove context propagation, hook option state versus the ListBox's withCollection-derived state, label/description associations, empty state and same layout instance passed as useComboBox's layoutDelegate. Constructing RAC leaf components outside their collection builder or passing plain Nodes without render would not satisfy that renderer. This bridge should get a small exact-source/type/behavior proof before a broader candidate is proposed.

Public RAC Popover can likewise retain its existing motion, trigger-width observation, placement and dismissal if supplied the lower state using publicly exported `OverlayTriggerStateContext` from `react-aria-components/Dialog`, an explicit real triggerRef, popover ref, isNonModal, placement/offset/containerPadding and existing class. This avoids replacing its private animation machinery. A pure usePopover+Overlay implementation is public but must recreate entry/exit mounting, CSS data-entering/data-exiting, portal/focus restoration, width and group geometry. It is not equivalent just because it returns a positioned div. Neither route authorizes disabling ancestor-scroll dismissal, focus management, normal motion, native pointer shielding or CSP.

The current app uses createRoot/StrictMode rather than hydration (`web/src/main.tsx`). A prebuilt data collection can be available synchronously under StrictMode; no delayed collection latch is required. Any reusable/server implementation still must keep generated IDs/ref/state per component/request and let React Aria own SSR IDs and hydration. Avoid a module global React element tree carrying component-owned IDs. No SSR benchmark or acceptance is claimed.

## Why it is a distinct benchmarkable experiment, and limits

The rejected rendering memoization report records 1.132% local complete-gate improvement and was restored. The rejected lazy More options variant deferred mounting an entire source-control subtree behind a native toggle and exposed immediate first-open Tab behavior. A prebuilt complete collection instead keeps the input, summary subtree and all logical choices available immediately and removes the hidden representation, not availability. It affects both picker collections, not only the unopened source control. Those structural distinctions justify an isolated feasibility/functional prototype if root later authorizes one; they do not predict speed or prove keyboard equivalence.

A material benchmark should first establish the absence of RAC hidden collection construction, while retaining the original complete logical collection/IDs/order/text and all existing exact expectations. Separate closed initial construction/unopened parent renders from first open/full-row mount/filter/close/reopen; keep baseline/current Virtualizer/prebuilt-collection variants distinct so hidden-tree and open-row effects are not attributed to each other. Normal-motion immediate native summary Enter/Space→Tab, both fields' controlled/custom/alias/invalid/no-match cases and actual owned focused-descendant identity/geometry are necessary functional controls. No replacement oracle, timeout sleep, force-click, slicing or weakened state assertion is suggested.

**Feasibility verdict:** public complete-collection override is concrete and removes a structurally different representation; a public-only nonvirtualized lower-hook prototype appears implementable. Preserving all RAC behavior is nontrivial. Public RAC state/overlay bridges could reduce that scope but remain unproven. No prototype was implemented or tested here.

**Implementation/CI verdict:** frozen Virtualizer acceptance remains with its independent reviewers and root gates; this report offers no verdict on them. No performance observation/projection, Linux timing, target savings, adoption or original objective resolution follows from source feasibility.
