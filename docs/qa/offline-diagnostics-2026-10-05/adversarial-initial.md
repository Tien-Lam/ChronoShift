Independent path derivation:

* App starts setupOffline once in a mount effect. Convert-to field focus does not directly register a worker or initiate readiness checking. A window focus handler refreshes only device timezone. This does not demonstrate that field opening cannot coincide with an outstanding readiness result/deadline.
* A new worker normally waits while the old worker controls a page. CHECK_READY probes the old controller's cache; new release availability does not change that identity. An incomplete old cache can produce exact warning while conversion and the new waiting worker remain usable.
* CHECK_READY silently catches repair rejection. The reported old uncaught install rejection and a caught readiness repair rejection must be distinguished.
* repair refetches every release asset instead of recovering intact ones from the controller cache. A single missing unchanged ancillary asset can therefore fail repair after a publication because an unrelated old immutable CSS/JS URL has disappeared from the hosted tree, or mutable index/release bytes have changed. This is a bounded competing failure path, not established user cause.
