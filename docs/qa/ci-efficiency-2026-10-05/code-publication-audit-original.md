## Actionable findings

1. **[P2] Fallback does not prove its actual deployment step succeeded.** The condition at root helper lines363–379 checks deploy job conclusion success, no successful reused deployment in prepare, and a complete successful verify/web job. It never checks deploy.steps for a successful deploy-pages action. For example, deploy `{ conclusion: success, steps: [] }` satisfies that part, contrary to the check name “actual deployment step ... succeeded.” This is a source counterexample, not an executed hosted run. Require the pinned actual deploy-pages step in fallback deploy, just as reuse requires it in prepare, plus explicit expected skipped reused-deployment step in preparation. Keep preparation/full-gate/deploy success guards. Record actual metadata names/pins when available; an absent or renamed expected step must fail, not be softened to job success.

2. **[P2] Optional branch-policy failure is misclassified as known absence.** ghOptional allows any nonzero command exit and parses whatever JSON it received. Lines333–345 treat every such result as HTTP404 Branch not protected. A 403 or 5xx API JSON response therefore skips required-policy checks, records a false absence claim, and can still reach the approved verdict. Malformed/empty JSON does throw and fail closed, but valid error JSON does not. Accept only a positively identified 404/Branch not protected response as the stated known absence; fail or record an explicitly unapproved unknown result for authentication/permission/service/other errors. Preserve the actual response/status/command evidence. For successful policy responses, reconcile both checks and legacy contexts, and match configured app identity/status where applicable, rather than silently iterating an absent checks array.

3. **[P2] Fallback no longer validates the CI artifact's release source tree.** The adaptation validates only pagesArtifact.release and resolves tested from the Pages release. Under fallback, the CI release/base is not checked at all. Assets matching does not independently establish the downloaded CI artifact's own source metadata, yet the report is intended to establish full trusted/tested artifact/source identity. Validate each release shape/base and independently resolve the CI release commit's tree to the reviewed head/main tree. Do not require CI release SHA equal expectedHead: build-offline.ts uses GITHUB_SHA, which can identify the PR synthetic merge commit. Tree equality is the intended invariant; Pages fallback should still explicitly identify the checked-out main SHA.

4. **[P2] Immutable asset comparison can pass vacuously.** Fallback filters both inventories to assets/ and compares JSON; empty inventories on both sides compare equal. Require a nonempty expected immutable asset inventory, preferably the manifest/entry-referenced runtime assets, before equality. The later index check prevents an entirely missing index from approving, but it does not prevent a release/index-only artifact from satisfying this specific “immutable runtime assets match” predicate. Keep the mode-dependent comparison: mutable release/SW metadata may legitimately differ for a fresh main fallback build, while immutable runtime asset bytes must match CI and every published file must match the actual Pages artifact.

These findings concern the evidence helper's predicates, not evidence that a production run took any of these paths. Source/workflow implementation approval from the earlier bounded review remains separate; this helper cannot yet be used as its final publication proof.
