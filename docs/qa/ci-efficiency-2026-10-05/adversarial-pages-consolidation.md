## Conditions that preserve existing delivery guarantees

- Keep workflow-level `pages-publication`, `cancel-in-progress:false`, around the entire reused and fallback paths, and preserve the existing shared deployment group where cross-workflow/rerun deployment serialization depends on it. Job-level deployment locking alone allows an older slow fallback gate to overtake a newer reused preparation. Both publishing branches must use main-only guards and the github-pages environment's main restriction. Concurrency provides exclusion, not a general ordering/queue guarantee; document bounded semantics rather than asserting FIFO. [GitHub deployment controls](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).
- Reused path deploys only after the reuse step explicitly returns the literal `true`, configure-pages succeeds and upload succeeds. The current helper catches lookup/digest/archive/tree errors and returns `false` to trigger the full gate. An ordinary miss must not become job failure that prevents fallback; a malformed/missing output must not become an accepted success. A setup failure must prevent deployment. Do not reuse stale local dist if preparation fails.
- Fallback/manual path must run the unchanged complete reusable Web gate and deploy only its successfully uploaded Pages artifact. Manual dispatch remains full verification. In a graph with reuse-and-deploy first, fullverify depending on its miss, and fallbackdeploy depending on verify, conditionals must distinguish 'successful reuse and deployment', 'successful miss requiring verification', 'failure' and 'skipped'. `always()` must never authorize deployment after a failed/canceled preparation or failed verification. Avoid dual publication for one run.
- Preserve all current trusted-run boundaries and required six successful gate names: correct workflow ID/path, same-repository PR event, completed success, matching head/main tree, tested release/main tree, artifact digest and safe members, size limits, correct `/ChronoShift/` release/base. Root checkout remains exact publishing tree. A cost improvement does not permit trusting runtime-byte equivalence or arbitrary PR artifacts instead of the exact source tree. Main-only checkout/code is the only executable input; extracted artifact remains static data.
- Combined job needs actions-read/contents-read for lookup and pages-write/id-token-write for deployment. Permissions are job-scoped, so preparation will have a more capable token than today's read-only prepare job. Keep it main-only, execute only trusted main scripts, retain pinned actions, do not run downloaded PR scripts or enable PR deployment/write triggers. `github-pages` environment protects the whole combined job, so an existing environment approval/delay could also delay preparation; record the changed scheduling behavior. [GitHub environment controls](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments), [custom Pages workflow requirements](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
- A job invoking a reusable workflow cannot also append arbitrary run/deploy steps. Combining a reused path therefore still needs a separate full-gate/fallback publication path or a larger reviewed refactor; it cannot skip verification just to fit one job. Same-job upload then deploy must use the same run's trusted Pages artifact; action success and deployment completion must be required, with final environment URL/output preserved. Match official deploy requirements for pages-write, id-token-write and the environment. [GitHub Pages workflow requirements](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
