## Candidate and falsification check

`scripts/serve-web.ts` eagerly calls `testReleases(root)` before announcing readiness whenever `CHRONOSHIFT_TEST_SERVER=1`. The global test server and every dedicated origin do this. `e2e/fixtures.ts` creates a dedicated server for all WebKit tests and every explicit isolated-origin case. Many ordinary WebKit app/layout/control journeys never POST `__test-release`, yet `scripts/test-releases.ts` reads runtime assets, constructs first/second/third renamed variants, rewrites worker protocols and recalculates each variant's complete integrity map. This work is semantically needed only when a synthetic release is published. The reporter deliberately collapses fixture names, so saved data cannot isolate variant generation time; do not attribute all121.470s inclusive fixture time or12.072s leaf time to this helper.

Candidate shape: retain the immutable `dist` source, dedicated per-test servers, testMode gating and existing response semantics; initialize one memoized variant-factory promise on the first synthetic-release POST, await it before validating/publishing that release, and keep the resulting maps for later transitions. Normal pre-publication requests should continue serving the unchanged production files. It must not rebuild artifacts, share mutable publication state among tests, serve retired assets, alter corrupt/interrupted/delayed fixtures, or weaken mixed-worker protocol/integrity failures.

Before any source edit or hosted run, the next local check should:

1. Measure existing `testReleases` construction against the same already-built root, with actual start/end clocks, wall and process CPU separately. Record asset hashes, cold/warm order and enough repetitions to show whether the cost is meaningful. No browser invocation is needed for this first disqualification check.
2. If material, use an isolated tooling prototype to compare startup plus first and later POST total cost. Count factory invocations: ordinary GET-only servers must invoke it zero times; concurrent first POSTs must invoke it exactly once. Deferring work into the first POST alone is not a speedup for release-changing journeys.
3. Compare every generated release/map entry byte-for-byte to the current factory; inspect sequential first→second→third, retained immutable variants, second-retired404s, malformed/unknown release rejection and a failed factory promise. Preserve bounded errors rather than silently serving incorrect files. Then run the existing targeted real-worker release/offline checks on separate origins, with all assertions unchanged, only if the prototype is worth implementing.

Risks: delayed initialization changes when fixture-generation failure surfaces; concurrent POSTs need one promise and deliberate error handling; moving work cannot be counted as removal; root/subpath identity and immutable test protocol must match. Reject the candidate if construction is negligible, first-POST end-to-end costs erase the GET-only saving, generated bytes differ, or lifecycle isolation changes. No speed boolean is sufficient. Any later hosted decision needs a correct reviewed candidate and comparable complete gate evidence.
