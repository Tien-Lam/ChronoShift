## Collection and lifecycle findings

`web/src/components/Choices.tsx:38–81` creates the unchanged ListBox/ListBoxItem surface, including value IDs, accessible label and description slots, check decoration and source/target hover policy. `Choices.tsx:128–156` creates module-level immutable option/search maps. The corrected dropdown report at `../../ci-efficiency-2026-10-05/dropdown-profile/report.md` establishes **454 options/2728 visible popup descendants** when fully open. Native full-list open/filter/clear/close script means are roughly24–44ms in that local Mac profile, with small layout deltas. The collection-lifecycle hypothesis is supported, but the profile's **negative CPU sample intervals invalidate weighted rankings**. Presence of ListBoxItem/DOMElement/cleanup frames is not a measured exclusive hook cost.

Installed library source narrows two tempting false leads:

- `react-aria-components/dist/private/ListBox.js:72–90` explicitly documents two child copies for ComboBox/Select: a hidden collection-building copy plus the real ListState copy. A closed native `<details>` hides rendering visually but leaves its React children mounted. `Popover.js:58–72` preserves children inside the hidden collection tree even while the real popover is closed. Therefore the unopened source ComboBox still constructs a full collection; the454/2728 popup count must **not** be assigned to its closed DOM or treated as a measured cold startup cost.
- `react-aria/dist/private/collections/useCachedChildren.js:15–61` already caches rendered children by stable object identity in a WeakMap. In production, a changed children callback alone does not recreate that WeakMap; dependencies control invalidation. Merely hoisting the row callback cannot remove per-row hook mounts on actual popup opening. ComboBox content itself depends on children/invalid/defaultItems (`ComboBox.js:61–83`), so parent renders can still revisit its hidden tree, but stable callback/memoization already produced only **1.557s/1.132%** whole local gate improvement and was rejected (`../../ci-next-2026-10-05/render-decision.md`). Do not repeat that experiment under a new label.

The normal-motion small-select close observation attributes the long wall interval to entry-animation lifecycle plus protocol/assertion observation, with only10–33ms observed after-removal margin. Waiting for entry before closing relocates real elapsed time. Motion suppression or dropping immediate-close coverage would violate the task.

## Recommended bounded candidate: defer unopened More options

The root's suggestion is structurally distinct from memoization and virtualization. Current `App.tsx:598–698` mounts source ZoneChoice, DateChoice, Numeric dates Select, Time display Select and logging/reset controls inside initially closed `<details className="options">`. Defer **that existing inner subtree** until the first actual opening, then keep it mounted for the remainder of the App lifetime. Preserve the native details/summary element and existing markup, CSS, imports, source/target independence, filters, options, event ownership and callbacks. A one-way `hasOpenedOptions` state is sufficient; it must not be reset on closing, resize, theme changes, reset preferences or conversion updates.

This removes cold hidden source-collection/date/select initialization and all revisits of those components during draft/result updates on pages that never open More options. It cannot eliminate the still-visible target ComboBox collection, nor any source collection cost after opening. It shifts the first-open initialization onto a deliberate user action; full controls journeys still pay that initialization once. That tradeoff must be evaluated with first-open responsiveness, not just navigation timings.

Required invariants and failure paths:

1. **Initial conversion/invalid preferences.** Parent already owns `prefs`, source/target resolution, reference date and validity. Initial reference validity is true with an empty date. `DateChoice.tsx:25–52` reports blank/uncommitted state true; `referenceValidityChanged` deduplicates unchanged validity. Omitting initial blank DateChoice cannot hide a user-created partial date because no user could yet edit an unmounted control. Source/target errors and preference-save gating remain in the parent.
2. **Partial-date retention after close.** After first opening, never unmount DateChoice on close. It stores uncommitted segment state inside React Aria, independent of parent's committed `referenceDate`. Closing while incomplete must preserve `referenceValidity.current=false` and block conversion; reopening must retain the partial segments. `DateChoice`'s existing `key={referenceReset}` remains the sole deliberate parent reset boundary.
3. **Reset and clear.** Preserve `clearDate`'s internal input reset, parent reference reset, true validity, logging reset and request/copy/import invalidation. Reset must not set the latch false or create a second unintended DateChoice remount on closing/reopening.
4. **Native first-open interaction.** A native toggle event is queued/coalesced. Verify mouse opening, keyboard Enter/Space opening followed immediately by Tab, and rapid open/close/reopen. If using `onToggle`, only `currentTarget.open===true` can enable the latch. An early closed toggle must never remove the subtree. The first Tab must reach the expected field rather than skip it because native expansion precedes React mounting. A discrete summary-activation latch may be considered if this is reproduced, while preserving programmatic/native toggle handling; do not claim it necessary without evidence.
5. **Focus and overlays.** Preserve source/target actual aria-controls ownership, hover does not commit on Tab, deliberate arrow/Enter/pointer commits, long-label wrapping, empty/custom/invalid queries, independent fields, and native motion. Closing details with a popup or partial calendar edit open requires the same surrounding lifecycle behavior as current source. Keep the summary focus behavior native.
6. **No preference or conversion side effects on mount.** The one-way latch update itself must not invalidate a conversion, import or copy owner. First empty DateChoice's validity callback must remain a no-op in the parent. Date-only/source defaults already stored in parent must display when first opened.
7. **No coverage/privacy shortcut.** Retain all116 units/273 configured browser identities/nine capability skips/subpath checks and independent fixtures. Do not preopen details globally, change expected field accessibility, suppress motion, store input, fetch runtime code from CDN or weaken update ownership.

Credible impact: structurally removable work exists, especially on cold pages and unopened-page edit renders. The older258-case instrumented Linux control records360 navigations totaling91.251 aggregate test-seconds and332 page creates totaling81.039s, but those totals contain browser/protocol/cache/worker work and scheduling overlap; source collection cost is unisolated. They are **not** current273-case timing, exclusive CPU, or a74-second saving ceiling usable as a forecast. Exact current-gate navigation count and exclusive hidden initialization cost are absent. Recommend a bounded local cold/warm comparison and first-open/lifecycle verification before considering a whole Linux gate. No source or Actions implementation approval is implied by this analysis.

## Secondary production opportunities, with smaller or unknown bounds

**Worker prewarming with idle reuse.** Current `App.tsx:216–349` starts a new module worker **after** each250ms debounce, posts validated text/options, then terminates it on success/error; invalidation and cleanup terminate any owned worker. `worker.ts` imports Chrono/Temporal/zone/parser modules, and `parser.ts` clones/extends both parsers at module initialization. A request controller could initialize a worker while the first valid nonempty edit's debounce runs, retain an initialized idle worker after successful completion, and terminate an actively processing worker on any invalidation. This is a substantive lifecycle design, not stable callbacks.

A complete design must distinguish initializing/idle/active/failed/disposed states; assign message IDs and worker identity per request; install rejection/error handlers before dispatch; reject stale queued messages even on a reused worker; preserve composition cancellation, source/date/device invalidation,250ms debounce, limits and pending/error rendering; create `now` at dispatch rather than prewarm; terminate on error, active cancellation, unmount/page exit and explicit reset; clear request text/results from controller state and retain only module/parser initialization in idle memory. Do not retain canceled active workers merely to ignore their responses, because that loses hard CPU cancellation. Prewarm failures must retain the existing deferred error/recovery experience. Reusing a worker after `convert` returns an engine-error requires an explicit policy; conservatively destroy it rather than silently treating it as a clean idle worker.

Its retained local mean pending→settled times are **297.433ms Chromium,309.833ms Firefox,290.750ms WebKit**, leaving only **47.433/59.833/40.750ms** after the250ms debounce. Those remainders include **all** worker initialization, parsing, main-thread/result commit and scheduling/instrumentation, so they are optimistic local ceilings for removable startup cost, not isolated worker measurements. Fresh test contexts still require cold initialization; prewarming overlaps rather than removes it. No Linux saving or target-sized claim is supported. Do not prioritize this over a demonstrably larger current critical-path cost.

**Request-local parse reuse.** `convert.ts:296–315` reparses identical `r.text` under an identical `zoneRef` for both endpoints, and can reparse a context header per endpoint/choice. A per-convert cache keyed by exact text plus exact reference offset/instant could reuse ParsedResults read-only; it must preserve endpoint choice, textual indices, contextual calendar rollover, ambiguous choices and both fixture corpora. It must never be keyed only by zone name/date or persist input beyond the request. No parse CPU attribution establishes material gate impact. Parsing source and target are independent; target-only caching across user actions is unsafe without an exact reference-instant contract, because current requests choose a fresh `now` and relative timestamps can change.

**Exact one-edit city lookup.** `zones.ts:161–188` computes full Levenshtein matrices for every city on non-exact queries even though resolveCity only accepts distance<=1. Keep public `editDistance` semantics intact; resolveCity can use a bounded one-edit predicate with a length-difference filter and linear scan, preserving Unicode normalization/UTF-16 behavior, short-name rejection and unique-match ambiguity. This reduces a known algorithmic cost for unknown/fuzzy city prose, but no retained timing establishes current-gate scale. It is an algorithmic candidate, not evidence that ordinary conversion or CI becomes74s faster.

## Verdict and gaps

Recommend the **one-way lazy More options subtree** as the clearest new bounded runtime candidate for investigation. Its lifecycle design can preserve current semantics, and its removed work differs from rejected memoization/virtualization. It still lacks isolated cold-cost measurements, current Linux attribution, first-open responsiveness and executed partial-date/keyboard/focus journeys. Worker and engine opportunities are concrete but have smaller or unmeasured impact. **No runtime candidate is currently proved target-sized; the original CI efficiency goal remains unresolved.**
